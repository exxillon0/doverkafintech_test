# LIMITS.md — что не сделано и почему

Документ честно фиксирует границы решения на момент сдачи. Задание
прямо говорит: «воспроизводимый Level 1–2 с честным LIMITS.md лучше
недоделанного "всё сразу"». Ниже — по категориям.

Структура каждой записи: **Что не сделано → Почему → Влияние → Что
нужно, чтобы закрыть**.

---

## 1. Доставка (Level 2)

### 1.1. Stage-джоба в CI отсутствует

- **Что**: CD деплоит только `prod` (push в `main`). `make deploy ENV=stage`
  работает локально, но автоматического прогона на stage из CI нет.
- **Почему**: в проекте одно «настоящее» окружение; stage задуман как
  локальный/demo-контур для проверки пайплайна. Полноценный stage-host
  в рамках 72 часов не поднимался.
- **Влияние**: нельзя показать «задеплоили на stage → прогнали e2e → потом
  на prod». Ревьюер может воспроизвести stage локально через
  `make deploy ENV=stage APP_VERSION=dev`.
- **Что нужно**: отдельный runner/host для stage, `workflow_dispatch` или
  отдельная job `cd-stage` с `concurrency: deploy-stage`,
  GitHub Environment `stage` с required reviewers перед промоушном на prod.

### 1.2. Автооткат не покрыт автотестом

- **Что**: механика автоотката (`rollback.sh` + `continue-on-error` в `cd`)
  проверена вручную: сломали `smoke.sh` → прогнали CI → откатились на
  предыдущий SHA. Автоматического теста, который прогоняет этот сценарий
  на каждый PR, нет.
- **Почему**: тест автоотката требует поднятого окружения и «плохой»
  версии образа; в рамках одного раннера GitHub Actions это дорого и
  хрупко.
- **Влияние**: регрессия в `rollback.sh` может остаться незамеченной до
  реального инцидента.
- **Что нужно**: отдельный «chaos»-прогон по расписанию
  (`schedule: cron`) на выделенном stage-окружении; либо integration-тест
  с docker-in-docker.

### 1.3. Trivy блокирует только `CRITICAL`

- **Что**: `--severity CRITICAL --exit-code 1` — gate. `HIGH` — только лог,
  `--exit-code 0`.
- **Почему**: базовые образы `python:3.12-slim` и `postgres:13.14`
  содержат `HIGH` CVE, часть — без фикса. Блокировка на `HIGH` остановила
  бы пайплайн «навсегда» без возможности починить.
- **Влияние**: `HIGH`-уязвимости могут уехать в прод.
- **Что нужно**: SLA на триаж `HIGH` (раз в неделю), `.trivyignore` с
  обоснованием по каждой CVE, постепенный переход на `--exit-code 1` для
  `HIGH` после апгрейда базовых образов.

### 1.4. Нет проверки подписи образов (cosign / sigstore)

- **Что**: образы пушатся в GHCR, но не подписываются. `cd` доверяет
  registry по факту `docker pull`.
- **Почему**: не входит в Level 2, добавляет заметную сложность
  (keyless OIDC, Fulcio/Rekor).
- **Влияние**: компрометация GHCR-аккаунта → компрометация прода.
- **Что нужно**: `cosign sign` в `ci`, `cosign verify` в `cd`, политика
  «deploy only signed images».

## 2. Секреты (Level 3)

### 2.1. Vault работает в dev-режиме

- **Что**: `hashicorp/vault:1.15.4` запускается как `vault server -dev`.
  Токен (`VAULT_DEV_ROOT_TOKEN`) — dev-заглушка, данные в памяти, при
  рестарте контейнера всё теряется, аутентификации нет.
- **Почему**: задание прямо говорит «Vault (dev-режим)». Prod-режим с
  реальной инициализацией, unseal-keys, AppRole — вне рамок.
- **Влияние**: после рестарта Vault секреты нужно пересидить
  (`vault/seed.sh` делает это в `deploy.sh`, так что деплой
  самовосстанавливается). Для реального прода небезопасно.
- **Что нужно**: `vault server -config=...` с file-storage/Raft, unseal
  через KMS/HSM, AppRole для api/worker, ротация токенов.

### 2.2. Секреты для `prod` в CI — опциональны

- **Что**: `cd`-джоба берёт `VAULT_DEV_ROOT_TOKEN` из GitHub Secrets; если
  секрет не задан — генерирует эфемерный dev-токен и продолжает работу с
  `::warning::`. Для ревьюера это удобно (репо клонируется и работает),
  но означает, что «настоящий» секрет не обязателен.
- **Почему**: ТЗ требует, чтобы проект разворачивался «с нуля по README»
  без настройки — иначе ревьюер упадёт на первом шаге. Компромисс:
  ephemeral-токен для demo, реальный секрет — для прода.
- **Влияние**: нельзя отличить «настоящий прод» от «демо» по факту
  наличия секрета — только по явному `VAULT_DEV_ROOT_TOKEN` в настройках.
- **Что нужно**: для прода — required secret, отказ стартовать без него
  (`ALLOW_DEV_VAULT=0` для `ENV=prod` уже есть, но в CI fallback
  оставлен намеренно).

### 2.3. Ротация секретов не автоматизирована

- **Что**: `vault/seed.sh` записывает секреты один раз. Ротации
  (`POSTGRES_PASSWORD`, `RABBITMQ_PASSWORD`, `PROVIDER_API_KEY`) по
  расписанию нет.
- **Почему**: Level 3, требует координации с перезапуском контейнеров.
- **Влияние**: скомпрометированный секрет живёт до ручной ротации.
- **Что нужно**: Vault dynamic secrets (database secrets engine для
  Postgres), либо cron-job с `vault write` + `docker compose up -d --force-recreate`.

## 3. Надёжность (Level 3)

### 3.1. Нет DLQ и лимита повторов для «ядовитых» сообщений

- **Что**: `worker` читает из очереди RabbitMQ. Если сообщение вызывает
  исключение, оно либо теряется (nack без requeue), либо крутится в
  retry-петле — зависит от реализации consumer'а. Dead-letter exchange
  не настроен, счётчика попыток нет, алерта на «ядовитое» сообщение нет.
- **Почему**: Level 3, требует правок в `worker/consumer.py` и
  `rabbitmq`-политике.
- **Влияние**: одно «плохое» сообщение может зациклить consumer и
  остановить обработку всей очереди.
- **Что нужно**: `x-dead-letter-exchange` на очереди, `x-message-ttl`,
  `max_retries` в коде, счётчик `worker_poison_messages_total`,
  алерт на рост DLQ.

### 3.2. Рестарт-политики — `unless-stopped` без backoff

- **Что**: у всех сервисов `restart: unless-stopped`. Docker перезапускает
  контейнер бесконечно, без экспоненциального backoff.
- **Почему**: стандартное поведение compose, достаточное для Level 2.
- **Влияние**: если сервис падает на старте (например, БД недоступна),
  он будет рестартовать в цикле, засоряя логи, вместо того чтобы
  «подождать» и упасть с алертом.
- **Что нужно**: `restart: on-failure:5` для критичных сервисов +
  healthcheck-based restart, либо переезд на orchestrator (k8s) с
  backoff.

### 3.3. Поведение при падении БД или RabbitMQ не проверено

- **Что**: `depends_on: condition: service_healthy` гарантирует порядок
  **старта**, но не поведение при падении в рантайме. API на каждый
  запрос открывает `psycopg.connect` — при недоступной БД вернёт 500,
  healthcheck продолжит отдавать «ok» (потому что `/health` не проверяет
  БД), reverse-proxy продолжит слать трафик.
- **Почему**: Level 3, требует доработки `/health` (`/health/db`,
  `/health/rabbit`).
- **Влияние**: reverse-proxy не отцепит «больной» api, пока контейнер
  жив. На защите могут сломать БД и спросить «почему трафик идёт».
- **Что нужно**: разделить liveness/readiness; readiness проверяет БД и
  RabbitMQ; при недоступности — отдавать 503, чтобы LB (nginx) убрал
  инстанс.

### 3.4. Бэкап БД не автоматизирован и не проверен на восстановление

- **Что**: `pgdata` — docker-volume. `pg_dump` по расписанию не делается,
  восстановление из бэкапа ни разу не прогонялось.
- **Почему**: Level 3, требует внешнего хранилища (S3/MinIO) и cron.
- **Влияние**: при потере volume данные не восстановить. Для финтеха
  (переводы) это критично.
- **Что нужно**: cron `pg_dump | gzip | aws s3 cp`, retention 7/30/365,
  **обязательный** restore-drill (раз в месяц, документировать в
  RUNBOOK), PITR через WAL-archiving.

## 4. Наблюдаемость (Level 4)

### 4.1. Только инфраструктурные метрики, бизнес-метрик нет

- **Что**: `prometheus` собирает стандартные метрики (если exporter'ы
  настроены). RED-метрики для api (rate/errors/duration) и бизнес-метрики
  (переводы по статусам, возраст самого старого `PENDING`) — не сделаны.
- **Почему**: Level 4 (бонус), требует инструментирования приложения.
- **Влияние**: дашборд «платежи работают?» за 10 секунд не собирается.
- **Что нужно**: `prometheus_client` в api/worker, `/metrics` endpoint,
  метрики `transfers_total{status="..."}`, `transfer_age_seconds`,
  Grafana-дашборд.

### 4.2. Алертов нет

- **Что**: `prometheus` собирает (возможно) метрики, но `alertmanager`
  не настроен. Никто не узнаёт о падении сервиса, росте очереди,
  устаревании PENDING-переводов.
- **Почему**: Level 4.
- **Влияние**: инциденты обнаруживаются глазами пользователей.
- **Что нужно**: `alertmanager`, rules в `prometheus`, каналы
  (email/Slack/Telegram), обоснование порогов в `RUNBOOK`.

### 4.3. Мета-мониторинг отсутствует

- **Что**: если `prometheus` сам упал, никто об этом не узнает. «Молчание
  сервиса ≠ "всё хорошо"» — не реализовано.
- **Почему**: Level 4, требует внешнего watchdog.
- **Влияние**: тихий отказ мониторинга = слепой прод.
- **Что нужно**: `watchdog` (healthchecks.io / dead-man-switch) на
  cron-пуш из prometheus; алерт «нет метрик 5 минут».

### 4.4. Нет `request_id` и структурированных логов

- **Что**: логи пишутся в `json-file` без `request_id`. `api` не
  пробрасывает `X-Request-ID`. `worker` не логирует `transfer_id` в
  каждой строке.
- **Почему**: Level 3, требует правок в приложении.
- **Влияние**: нельзя проследить перевод end-to-end по логам.
- **Что нужно**: middleware в `api` (генерация/проброс `X-Request-ID`),
  contextvar в `worker`, structured logging (`structlog` / `python-json-logger`).

### 4.5. Ротация логов — только `max-size` / `max-file`

- **Что**: `json-file` с `max-size: 10m`, `max-file: 3` на контейнер.
  Централизованного сбора (Loki/ELK) нет.
- **Почему**: достаточно для одной машины, Level 2.
- **Влияние**: при переезде на несколько хостов логи не собрать.
- **Что нужно**: `promtail` → `loki`, либо `fluent-bit` → `elasticsearch`.

## 5. Инфраструктура и воспроизводимость

### 5.1. Всё на одном Docker-host

- **Что**: `docker-compose.yml` поднимает все 8 сервисов на одной машине.
  Нет разделения на control-plane / data-plane, нет anti-affinity.
- **Почему**: рамки задания — «Docker Compose v2 на чистой машине».
- **Влияние**: падение хоста = падение всего стека. Нет горизонтального
  масштабирования.
- **Что нужно**: переезд на k8s (или Nomad), либо хотя бы разделение
  «db/rabbitmq — отдельный хост».

### 5.2. Одна реплика каждого сервиса

- **Что**: `api:1`, `worker:1`, `mock-provider:1`.
- **Почему**: advisory lock в `migrate.sh` — превентивный, на случай
  масштабирования; реально реплик всегда одна.
- **Влияние**: нет zero-downtime обновлений. `docker compose up -d`
  пересоздаёт контейнер — короткий downtime есть.
- **Что нужно**: `deploy: replicas: 2` для api (за reverse-proxy),
  worker — конкурентные consumer'ы с `prefetch_count`, rolling update
  через `docker compose up -d --no-deps --scale`.

### 5.3. Rollback-стратегия БД — только expand→contract

- **Что**: `rollback.sh` откатывает **код**, но не схему. Для ломающих
  миграций (`RENAME`, `DROP COLUMN`) откат кода сломает приложение;
  единственный путь — restore из бэкапа (которого нет, см. 3.4).
- **Почему**: осознанное решение (см. `DECISIONS.md`), классика
  expand→contract. В рамках 72 часов полноценный `migrate down` не
  писался.
- **Влияние**: если кто-то нарушит правило «RENAME/DROP отдельным
  релизом», откат станет ручным и болезненным.
- **Что нужно**: `NNN__*.down.sql` для каждой миграции + `migrate.sh
  --down N`, **плюс** автоматический бэкап перед каждой миграцией.

### 5.4. Нет e2e-теста «положил перевод → он дошёл до COMPLETED»

- **Что**: `smoke.sh` проверяет `/health` и `pg_isready`. Сквозного
  сценария (POST /transfers → worker обработал → статус COMPLETED) нет.
- **Почему**: требует mock-provider + реальной очереди + ожидания;
  в smoke это замедлило бы деплой.
- **Влияние**: smoke может быть зелёным, а бизнес-логика сломана.
- **Что нужно**: отдельный `make e2e` с `curl POST /transfers` и polling
  `GET /transfers/{id}` до `COMPLETED`/`FAILED` с таймаутом 30с.

## 6. Процесс

### 6.1. Один разработчик, 72 часа

- **Что**: нет code review, нет обязательных approvals, нет
  branch protection. `main` пушится напрямую.
- **Почему**: соло-разработка в рамках тестового.
- **Влияние**: регрессии ловятся CI, но не ревью.
- **Что нужно**: branch protection (required PR, required checks),
  `CODEOWNERS`, минимум 1 approve.

### 6.2. Нет staging→prod promotion gate

- **Что**: push в `main` сразу едет в прод. Нет «approve to prod».
- **Почему**: одно окружение, см. 1.1.
- **Влияние**: любой баг в `main` = баг в проде через 2 минуты.
- **Что нужно**: GitHub Environments (`stage` → `prod`) с required
  reviewers; `workflow_dispatch` с параметром `environment`.

### 6.3. `docker compose down -v` не запрещён на уровне tooling

- **Что**: в скриптах деплоя `down -v` нет (это осознанно), но ничто не
  мешает разработчику выполнить его руками.
- **Почему**: shell — есть shell.
- **Влияние**: случайный `docker compose down -v` снесёт `pgdata`.
- **Что нужно**: alias/wrapper `docker` → `safe-docker` (отказывается
  от `down -v` без `--i-know-what-i-do`), либо переезд на managed DB
  (RDS), где volume не в docker.

## Что **сделано** (чтобы не сложилось впечатление «всё плохо»)

- Level 1: pinning версий, multi-stage, non-root, `.dockerignore`,
  healthcheck'и, `depends_on: condition: service_healthy`, секреты не в
  образах.
- Level 2: CI (lint/test/build/scan/тег по SHA), CD через
  `make deploy ENV=…`, миграции **до** раскатки, `pg_advisory_lock`,
  smoke после деплоя, автооткат, `RUNBOOK` про схему БД.
- Документация: `README`, `ARCHITECTURE`, `DECISIONS`, `ASSUMPTIONS`,
  `RUNBOOK`, `LIMITS` (этот файл).
- Доказательство CI: успешный прогон в Actions —
  https://github.com/exxillon0/doverkafintech_test/actions/runs/42389989594

## Приоритеты, если будет ещё время

1. `pg_dump`-бэкап + restore-drill (риск потери данных — самый высокий).
2. `/health/db`, `/health/rabbit` + разделение liveness/readiness.
3. DLQ для worker.
4. Stage-джоба в CI + GitHub Environment для prod.
5. `request_id` + structured logging.
